# 6. Breaking changes come from commit footers, and the changelog is prepended

Date: 2026-08-14

## Status

Accepted.

## Context

The changelog is generated by `git-cliff` from the commit history. Twice — for
v0.4.0 and again for v0.4.1 — a "Breaking Changes" section was written into
`CHANGELOG.md` by hand and then silently erased.

Two independent faults produced that:

1. **The template never emitted breaking changes.** It printed
   `commit.message` grouped by type, and nothing else. `commit.breaking` and
   `commit.breaking_description` were not read, so a commit marked `!` or
   carrying a `BREAKING CHANGE:` footer looked exactly like any other commit.
   A hand-written section had no source in the history, so regeneration
   dropped it.

2. **The regeneration rewrote the whole file.** `git-cliff --tag vX.Y.Z -o
   CHANGELOG.md` reproduces every release from scratch. Anything not derivable
   from a commit cannot survive it, by construction.

The change that went missing was real: v0.4.0 raised the minimum supported Rust
version from 1.88 to 1.89, which fails the build for anyone on the older
toolchain. It arrived as `chore(deps): update the toolchain and dependencies` —
an ordinary, non-breaking commit message — and `^chore` is `skip = true` in the
parsers, so even a correct template would not have seen it.

## Decision

**A breaking change is announced by the commit that makes it**, using
Conventional Commits' own mechanism: a `!` after the type and a
`BREAKING CHANGE:` footer describing the break in the words a reader needs.
The changelog section is rendered from that footer, so it cannot drift from the
commit and cannot be lost.

Three parts implement it in `cliff.toml`:

- The template emits a `### Breaking Changes` section from
  `commits | filter(attribute="breaking", value=true)`, printing
  `breaking_description` and falling back to the subject line when a commit is
  marked `!` without a footer.
- The ordinary type groups filter breaking commits *out*, so a commit appears
  once rather than twice.
- `protect_breaking_commits = true` (already set) exempts a breaking commit
  from `skip`, which is what lets a `chore(deps)!` reach the changelog at all
  despite `^chore` being skipped. Verified against the real repository rather
  than assumed: a probe commit `chore(deps)!` with a `BREAKING CHANGE:` footer
  was rendered under Breaking Changes with the footer text, while ordinary
  `chore` commits stayed absent.

**Regeneration uses `--prepend`, not `-o`.** `git-cliff --tag vX.Y.Z
--unreleased --strip header --prepend CHANGELOG.md` writes only the new version
on top and leaves every earlier entry untouched. The whole-file rewrite is what
made hand edits perishable, so it is no longer part of the release ritual.

`--strip header` matters: without it the file's title block is prepended along
with the new section, leaving two of them.

The release workflow is unaffected: it runs `--latest --strip header` into
`RELEASE_NOTES.md`, which never touches `CHANGELOG.md`.

## Consequences

- A breaking change that is not marked in its commit still goes unannounced.
  This is the intended trade: the mark is the single place the author states
  the break, and a reviewer can see it in the commit rather than trusting that
  the changelog was edited afterwards.
- The v0.4.0 MSRV note stays where it was written by hand. Its commit is
  already tagged and published, and rewriting a released tag to fix a
  changelog line costs more than it returns. `--prepend` keeps it from being
  erased again.
- A dependency bump that raises the MSRV is a breaking change and is committed
  as `chore(deps)!` with a footer, even though `chore` is otherwise invisible
  to the changelog.
